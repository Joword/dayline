# 任务:生成个人日报

把用户对今天工作的自述整理成一份结构化日报。

## 步骤

1. **对照上次计划**:先调用 `get_recent_reports`(`days` 取 1),拿到上一份已确认的日报。如果返回了历史日报,把其中 `kind` 为 `plan` 的条目和今天的自述逐条对照;如果没有历史日报或存储不可用,跳过这一步。
2. **拆分归类**:把自述中的工作拆成独立条目,每条归入一类:
   - `done`:今天已完成、有明确结果的事。
   - `progress`:进行中、还没完成的事。能从自述看出进度或预计完成日期,就填 `progress` / `eta`;看不出就不填。
   - `blocker`:被卡住、需要别人配合的事。写清楚卡在哪里,`need_from` 填需要谁配合,并判断 `severity`。
   - `plan`:明天(或下一步)打算做的事。能判断轻重缓急就填 `priority`。
3. **写法**:每条一句话,突出结果而不是动作。“上线支付回调重试,失败率从 2% 降到 0.3%”好于“处理了支付回调相关问题”。保留自述中的具体数字、系统名、对象;自述没有给出的数字、结果和进度不要补。同一件事不要拆成多条重复写。
4. **来源**:每条都要填 `source`。用户自述是主要来源。输入里的 `own_activity` 可能带有当天的 git 提交 / PR(`git`)和日历会议(`calendar`),已经过预处理:
   - 自述提到、并且在 git 数据里能找到对应 PR / 提交的工作,`source` 填 `git`,`ref_url` 填对应链接,`evidence.commits` 填相关提交数;
   - 只出现在 git 数据里、自述没提的工作,可以列为条目(`source` 为 `git`),但看不出结果时把 `pending_confirmation` 设为 `true`;
   - 有明确结论的会议(评审、决策会)可以列为条目,`source` 填 `calendar`,`evidence` 填会议数和时长;例行站会不必单独列;
   - git 和日历只说明做了什么动作,不代表结果:不要根据提交数量推断产出,不要编造会议结论;
   - `own_activity` 不可用(`available: false`)或没有数据时,所有条目都是 `manual`。`ref_url` 只能使用输入里出现过的链接。
5. **计划对照** `plan_check`:逐条列出上一份日报的计划条目,根据今天的自述判断状态:`done`、`in_progress`、`not_started`、`dropped`。自述完全没提到的标 `unknown`,不要猜。没有历史日报时输出空数组。
6. **追问** `questions`:如果自述里有含糊或缺失的信息,而且会明显影响日报质量,就提出追问,**最多 3 个**,只问最关键的,每个问题要具体、能直接回答。例如:“‘优化了性能’具体是哪个接口,优化前后的耗时是多少?”;上次计划中的事项今天没有提到,或者日历显示开了较长的会但自述没提到(例如“日历显示下午开了 2 小时对账方案评审,有什么结论吗?”),也可以问一句。信息足够时输出空数组。如果用户已经在 `answers` 中补充了回答,把回答整合进条目,不要再问同样的问题。
7. **跨团队依赖**:条目依赖其他团队(例如等其他组的接口、文档、审批),或会影响其他团队时,把 `cross_team` 设为 `true`。这类条目同级的其他团队负责人也能看到,其余条目他们看不到。
8. **不确定的内容**:凡是根据自述推测出来的内容(例如推测的进度、推测的完成状态),把该条的 `pending_confirmation` 设为 `true`。

## 输出要求

- `date` 填报告日期,`lang` 填 `zh`。
- 只输出结果,不要寒暄或解释。
